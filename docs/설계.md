# 모임 알림장 — 데이터 처리 설계 & 업무 분담

> 근거 자료: 기획안 ppt(p.8~12), 콘텐츠 데이터 구성.pdf, 앱 예시화면.pdf
> 원칙: 바닐라 JS + HTML/CSS, 루트 `index.html`, `main` 브랜치만 사용

---

## 1. 앱 한 줄 요약

모임 주최자가 **시간·장소·준비물·유의사항·정산**을 링크 하나에 담아 카톡으로 보내고,
참석자는 그 링크에서 **응답 → 캘린더 저장 → 당일 안내 확인 → 입금**까지 끝내는 웹앱.

## 2. 꼭 필요한 기술 결정: 서버 저장소

참석자가 **자기 휴대폰**에서 누른 "참석"이 **주최자 화면**의 참석 현황에 보여야 합니다.
브라우저 저장소(localStorage)는 기기마다 따로라서 이게 불가능합니다.
심사 체크리스트(p.17)의 "조원 3명 동시 접속 테스트"도 통과하지 못합니다.

**권장안: Vercel Functions + Upstash Redis (Vercel Marketplace, 무료 플랜)**

| 항목 | 내용 |
|---|---|
| 프론트 | `index.html` + 바닐라 JS (해시 라우팅 `#/e/abc123`) |
| API | 저장소 `api/` 폴더의 JS 파일 → Vercel이 자동으로 서버 함수로 실행 (프레임워크 없음) |
| DB | Upstash Redis — Vercel 대시보드에서 연결하면 키가 환경변수로 자동 주입됨 (코드·깃에 키가 안 남음) |
| 로그인 | 없음. 주최자는 만들 때 받은 **수정 토큰**을 브라우저에 보관 → "내 알림장"에 표시 |

> 대안: Supabase(브라우저에서 바로 호출). 단, 키가 프론트 코드에 노출되고 보안 규칙(RLS)을 따로 짜야 해서 기간 대비 위험이 큼.

## 3. 저장 데이터 모델

**사용자가 입력하거나 행동해서 생기는 값만 저장**하고, D-Day·인원 집계·1인당 금액처럼 계산되는 값은 저장하지 않고 화면에서 매번 계산합니다(값이 어긋날 일이 없음).

### 3-1. `event:{id}` — 안내장 (주최자가 씀)

```js
{
  id: "k3f9a2",                // 링크에 쓰이는 짧은 ID
  editTokenHash: "…",          // 주최자 수정 권한 확인용 (원본 토큰은 주최자 브라우저에만)
  createdAt, updatedAt,        // ISO 문자열

  // ── 사용자 입력 데이터 (콘텐츠 데이터 구성 1) 안내장 만들기)
  title: "가을 동아리 모임",     // 필수
  date: "2026-10-31",          // 필수
  startTime: "17:00",          // 필수
  endTime: "20:00",            // 선택 (빈 문자열 허용)
  placeName: "하이브 라운지 3층", // 필수
  address: "",                 // 선택
  expectedCount: 20,           // 선택 (null 허용)
  fee: 16000,                  // 선택, 1인 참가비 (null 허용)
  supplies: "개인 컵, 간단한 간식", // 선택
  notes: "주차 2시간 지원돼요.",   // 선택
  hostName: "김민지",           // 선택 (당일 모드 연락처용)
  hostPhone: "",               // 선택

  // ── 변경 이력 (수정·재공유)
  changeVersion: 0,            // 수정 저장할 때마다 +1
  changes: [                   // 가장 최근 수정분
    { field: "placeName", before: "하이브 라운지 3층", after: "역삼 모임공간 B 4층", at: "…" }
  ],

  // ── 정산 (정산 안내 화면에서 등록, 등록 전에는 null)
  settlement: {
    total: 224000,             // 총 비용 (필수)
    count: 14,                 // 정산 인원 (필수)
    mode: "equal",             // "equal"(균등) | "custom"(개인별 조정)
    custom: { "<participantId>": 16000 }, // mode가 custom일 때만
    accountNo: "[은행명] 000-0000-0000", // 필수
    accountHolder: "김민지",    // 필수
    sentAt: "…"
  }
}
```

### 3-2. `event:{id}:p` — 참가자 (Redis 해시, 참가자 1명 = 필드 1개)

참가자를 안내장 문서 안에 배열로 넣지 않고 **따로 저장**합니다.
여러 명이 동시에 "참석"을 눌러도 서로의 응답을 덮어쓰지 않게 하기 위해서예요.

```js
// 필드 이름 = participantId, 값 =
{
  id: "p_7xk2",
  name: "송다은",               // 필수
  rsvp: "yes",                 // "yes"(참석) | "maybe"(미정) | "no"(불참)
  settle: "unpaid",            // "done"(정산 완료) | "unpaid"(미정산) | "excluded"(정산 제외)
  seenVersion: 1,              // 이 사람이 "확인했어요"를 누른 changeVersion
  respondedAt, paidAt
}
```

참가자 본인 확인은 로그인 대신, 응답할 때 받은 `participantId`를 그 사람 브라우저에 저장해서 처리합니다.

### 3-3. 브라우저에만 저장 (localStorage)

| 키 | 값 | 용도 |
|---|---|---|
| `moim.hosted` | `[{ id, editToken }]` | 내가 만든 안내장 → "내 알림장" 목록, 수정 권한 |
| `moim.me.{eventId}` | `{ pid, token }` | 이 안내장에서의 "나" (token = 응답할 때 받은 본인 확인용 비밀값) |

## 4. 계산 규칙 — `js/calc.js` (콘텐츠 데이터 구성 '처리 규칙' 그대로)

모든 화면이 이 파일 하나만 쓰게 해서 규칙이 화면마다 달라지지 않게 합니다.
**입력 → 출력만 있는 순수 함수**라서 테스트하기 쉽습니다.

| 함수 | 규칙 | 쓰는 화면 |
|---|---|---|
| `dday(date, today)` | 모임 날짜 − 오늘 → `D-28` / `D-DAY` / `3일 전 종료` | 초대장, 내 알림장 |
| `isToday(event)` | 모임 날짜 = 오늘 → 당일 모드 | 내 알림장, 초대장 |
| `countRsvp(ps)` | 참석·미정·불참 각각 몇 명인지, 전체 응답 수 | 초대장, 참석 현황 |
| `defaultSettle(rsvp)` | 참석 → 미정산, 미정·불참 → 정산 제외 | 응답 저장 시 |
| `perPerson(total, count)` | 총 비용 ÷ 정산 인원, 1원 단위 올림 (끝전은 주최자 화면에 표시) | 정산 안내 |
| `settleSummary(ps, s)` | 정산 대상·완료·미정산 인원, 남은 금액 | 참석 현황 |
| `diffEvent(old, new)` | 바뀐 항목만 `{field, before, after}` 목록으로 | 수정·재공유 |
| `seenCount(ps, ver)` | `seenVersion ≥ changeVersion`인 인원 → "확인 13 / 15" | 초대장, 내 알림장 |
| `toICS(event)` | 모임명·날짜·시간·장소 → `.ics` 파일 (구글·애플 캘린더 공통) | 초대장 "캘린더에 추가" |

## 5. 화면별 데이터 흐름

```
[홈] ──모임장 만들기──▶ [01 안내장 만들기] ──POST /api/events──▶ 링크 생성 + 토큰 보관
                                                                  │
                         카톡 공유 (Web Share API / 링크 복사)      ▼
[참석자] ─링크─▶ [02 초대장 보기] ──참석/미정/불참──▶ POST rsvp ─────┐
                     │  캘린더에 추가(.ics) · 변경 "확인했어요"          │
                     ▼                                               ▼
[주최자] [내 알림장] ─▶ [03 참석 현황] ◀──── GET /api/events?id= (안내장 + 참가자)
                                  │ 정산 등록
                                  ▼
                       [04 정산 안내] ──POST settle─────▶ 참석자 화면에 금액·계좌 표시
                                                         참석자 "입금했어요" → settle: done
                                                         → 03 참석 현황에 반영
[주최자] [수정·재공유] ──diffEvent──▶ changes 저장, changeVersion+1 ──▶ 02에 "변경됐어요" 배너
[당일] 모임 날짜 = 오늘 ──▶ [D-DAY 당일 모드] (오시는 길·연락처·유의사항 우선 표시)
```

| 화면 | 읽는 데이터 | 쓰는 데이터 |
|---|---|---|
| 01 안내장 만들기 | — | event 생성 |
| 02 초대장 보기 | event, 참가자, 내 participantId | rsvp, seenVersion, settle=done(입금) |
| 내 알림장 | localStorage의 내 안내장 목록 → 각 event 요약 | — |
| 03 참석 현황 | event, 참가자 전체 | rsvp, settle 수동 변경 (주최자) |
| 04 정산 안내 | event, 참석자 목록 | settlement |
| 수정·재공유 | event | event 수정 + changes |
| 당일 모드 | event | — |

## 6. API — `api/events.js` 하나

| 요청 | 하는 일 | 권한 |
|---|---|---|
| `GET /api/events?ping=1` | 서버 저장소 연결 여부 → 없으면 앱이 체험 모드로 동작 | 누구나 |
| `GET /api/events?id=` | 안내장 + 참가자 목록 | 링크를 가진 사람 |
| `POST {action:'create', data}` | 안내장 생성 → `editToken` 반환 | 누구나 |
| `POST {action:'edit' / 'settle' / 'host', id, token, …}` | 안내장 수정 / 정산 등록 / 참가자 상태 변경 | `editToken` 필요 |
| `POST {action:'delete', id, token}` | 안내장 삭제 (참가자 응답·내 알림장 목록에서도 제거) | `editToken` 또는 만든 사람 로그인 |
| `POST {action:'rsvp', id, data}` | 참석 응답 (새 참가자) | 누구나 |
| `POST {action:'self', id, pid, ptoken, data}` | 본인 응답 변경·변경 확인·입금했어요·준비물·늦어요 | 응답 때 받은 `participantToken` 또는 로그인한 본인 (참가자 id는 공개 정보라 id만으로는 불가) |
| `POST {action:'signup' / 'login' / 'logout' / 'whoami'}` | 전화번호 + 비밀번호 가입·로그인 → `session` (30일) | 로그인 실패 10회면 15분 차단 |
| `POST {action:'mine', session}` | 내가 만든 모임(주최) + 응답한 모임(참여) | 로그인 필요 |
| `POST {action:'me', session, id}` | 이 안내장에서 내가 주최자인지, 이미 응답했는지 | CDN 캐시 대상 아님 |
| `POST {action:'claim', session, hosted, joined}` | 로그인 전 이 브라우저에서 만든·응답한 기록을 계정으로 옮김 | 관리·참가자 토큰 검증 |

**로그인** (설계: `docs/superpowers/specs/2026-10-04-login-design.md`): 안내장 만들기·내 알림장은 로그인 필수, 참석 응답은 선택. 주최자는 관리 토큰 **또는** 로그인한 만든 사람, 참가자 본인은 참가자 토큰 **또는** 로그인한 본인. 같은 계정은 한 모임에 한 번만 응답(다시 누르면 기존 응답 수정). 저장 키: `user:{전화번호}`, `session:{토큰}`, `user:{전화번호}:events`. 전화번호는 공개 응답에 포함하지 않는다.

입력 검증과 상태 변경 규칙은 `js/ops.js` 한 곳에 있고, 서버와 체험 모드가 똑같이 씁니다.

**동시 수정:** 서버는 값을 읽은 뒤 그 사이 다른 요청이 고쳤는지 비교하고(compare-and-set, Redis Lua), 바뀌었으면 최신 값에 다시 적용해 저장합니다. 그래서 주최자가 정산 상태를 바꾸는 순간 참석자가 "늦어요"를 눌러도 둘 다 남습니다.

**다른 기기에서 이어 쓰기:** 안내장을 만들면 **주최자 관리 링크**(`#/e/{id}?k=토큰`), 응답하면 **내 응답 링크**(`?p=&t=`)를 복사할 수 있어요. 토큰은 `#` 뒤에 있어 서버 로그에 남지 않습니다.

**누가 오나요? · 지도:** 초대장의 참석 현황에서 주최자가 아니어도 응답한 사람 이름을 참석·미정·불참별로 볼 수 있어요(이름만, 정산 정보는 주최자 화면에만). 주소를 입력한 안내장은 장소 아래 **네이버 지도에서 보기** 링크가 모두에게 보여요.

**변경 이력:** 수정할 때마다 `{version, field, before, after}`를 쌓고(최대 50개), 참석자에게는 본인이 확인한 버전 이후의 변경을 항목별로 합쳐 보여줍니다.

## 7. 파일 구조 (팀원별 담당 파일이 겹치지 않게)

```
index.html               ← 첫 화면 + 모든 화면의 틀 (이승현)
css/base.css             ← 색·글꼴·버튼·카드 공통 스타일 (이승현)
css/{화면}.css           ← 화면별 스타일 (각 담당자)
js/app.js                ← 해시 라우터 (이승현)
js/api.js                ← 서버 호출 + 로컬 모드(체험 모드) (이승현)
js/calc.js               ← 4장 계산 규칙 (이승현)
js/ui.js                 ← 공통 조각: 헤더, D-Day 배지, 토스트, 복사 버튼 (이승현)
js/views/home.js         ← 홈
js/views/create.js       ← 01 안내장 만들기 / 수정·재공유 (같은 폼 재사용)
js/views/invite.js       ← 02 초대장 보기 + 당일 모드
js/views/dashboard.js    ← 내 알림장
js/views/status.js       ← 03 참석 현황
js/views/settle.js       ← 04 정산 안내
js/ops.js                ← 입력 검증·상태 변경 규칙 (서버·체험 모드 공용) (이승현)
js/card.js               ← 안내장 카드 (만들기 미리보기·초대장 공용)
api/events.js, api/_store.js   ← 서버 함수 + Redis (이승현)
tests/*.test.js          ← 계산·처리·서버 테스트 (`npm test`)
tools/serve.py           ← 로컬 미리보기 서버 (`py tools/serve.py` → http://localhost:5173)
```

서버 저장소가 없으면 `js/api.js`가 자동으로 **체험 모드**(브라우저 저장)로 바뀝니다. 그래서 로컬에서도 모든 화면을 만들고 확인할 수 있어요.

## 8. 범위 — 마감(10/8 11:00)을 지키기 위한 우선순위

| 등급 | 기능 |
|---|---|
| **필수 (10/5 대면 점검 전)** | 안내장 만들기(+미리보기) → 링크 공유 → 초대장 보기 → 참석 응답 → 참석 현황 |
| **필수 (10/6까지)** | 정산 등록·1인당 계산·입금했어요, 수정·재공유(변경 배너·확인 수), 내 알림장, 캘린더 추가 |
| **차별점 (10/7까지)** | D-DAY 당일 모드, 모바일 화면 다듬기 |
| **여유 있으면** | 질문·답변, 준비물 담당 정하기, "늦어요" 버튼, 지도 보기 |

> 예시화면의 질문·답변, 준비물 담당, 늦어요는 기획안 핵심 기능(p.10)에 없는 추가 기능입니다. 킥오프 합의(핵심 1 + 보조 2)를 넘기므로 맨 마지막에 해요.

## 9. 빌드·개발 3인 업무 분담

### 기본 원칙
- **이승현(토큰 가장 많음) = 기반 + 서버 + 통합 담당.** 모든 화면이 기대는 공통 부분과, 가장 복잡하고 실수하면 전체가 망가지는 부분(동시 저장, 변경 이력, 배포)을 맡습니다.
- 나머지 두 명은 **화면 단위로** 나눠서 서로 같은 파일을 건드리지 않게 합니다.
- 브랜치를 안 쓰므로 충돌 방지 규칙이 중요합니다(아래).

### 같은 `main`에서 충돌 없이 일하는 규칙
1. **작업 시작 전 항상** `git pull --rebase`.
2. **자기 담당 파일만** 수정. `index.html`·`base.css`·`calc.js`·`api.js`를 고쳐야 하면 이승현에게 요청.
